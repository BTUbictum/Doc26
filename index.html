U-Home

Portal único de entrada a las herramientas internas de BT
Preparado para: Infraestructura, Arquitectura, Ciberseguridad, Consejo Técnico Elaboró: Héctor Herrera — Especialista BT Versión del documento: 1.0

1. Resumen ejecutivo

U-Home es el portal único de entrada (launcher) a las herramientas internas del equipo de Business Technology (BT) de Ubictum. Antes de su construcción, cada herramienta se distribuía por separado mediante enlaces sueltos (correo, chats, favoritos del navegador), sin un punto central de acceso ni un criterio uniforme de seguridad. U-Home resuelve ese problema concentrando el acceso a todas las herramientas de BT en una sola pantalla, con un inicio de sesión único basado en la cuenta corporativa de Microsoft 365 de cada colaborador.

El portal está publicado en https://btubictum.github.io/U-Home/ y es accesible para todo el personal activo de Ubictum (colaboradores internos) más los grupos de invitados de cada herramienta específica. Actualmente aloja 8 accesos, de naturaleza distinta entre sí (aplicaciones de Power Apps preexistentes, portales HTML construidos a la medida, y portales externos administrados por terceros) — esta distinción es central para entender el modelo de seguridad del proyecto y se explica a detalle en la sección 3.

1.1 Objetivos del proyecto

  • Concentrar en un solo punto de entrada todas las herramientas internas de BT, eliminando la dispersión de enlaces.
  • Unificar la experiencia de inicio de sesión: si el colaborador ya tiene sesión activa de Microsoft en su navegador, U-Home lo reconoce automáticamente, sin pedirle iniciar sesión de nuevo.
  • Dejar el control de acceso fino (quién entra a qué herramienta específica) en manos de cada aplicación individual registrada en Entra ID, no centralizado en el launcher — así cada equipo dueño de una herramienta mantiene el control de sus propios usuarios.
  • Reducir el costo de operación: hosting estático sin servidores propios, aprovechando licenciamiento de Microsoft 365 ya existente en la organización.

1.2 Alcance de este documento

Este documento cubre la arquitectura técnica de U-Home y de los portales HTML propios que aloja (Alertas Operativas, Biométricos Colaboradores, Colaboradores Ubictum y U-Formularios), el modelo de seguridad y control de acceso implementado en Microsoft Entra ID, la infraestructura de hosting y operación, y un inventario técnico completo en el Anexo. No profundiza en la lógica de negocio interna de cada herramienta — eso se documenta por separado, herramienta por herramienta; el foco aquí es cómo están construidas, dónde viven, y cómo se protegen.

2. Arquitectura

2.1 Patrón general

Todas las herramientas construidas a la medida por BT (U-Home, Alertas Operativas, Biométricos Colaboradores, y las que están en construcción: Colaboradores Ubictum y U-Formularios) siguen el mismo patrón arquitectónico: aplicaciones web estáticas de una sola página (HTML + CSS + JavaScript), sin servidor propio ni backend intermedio, que se autentican directamente contra Microsoft Entra ID y leen/escriben datos directamente contra Microsoft Graph API, usando listas de SharePoint como capa de almacenamiento (base de datos).

Flujo típico de una sesión:

  1. El colaborador abre la URL del portal (GitHub Pages) en su navegador.
  2. El JavaScript del portal (librería MSAL.js) intenta un inicio de sesión silencioso (ssoSilent / acquireTokenSilent) contra la app registrada en Entra ID de ESE portal específico.
  3. Si el colaborador ya tiene sesión activa de Microsoft y está autorizado para esa app (grupo de seguridad asignado), obtiene un token sin fricción — no ve ninguna pantalla de login.
  4. Si no hay sesión previa, o el token silencioso falla, se dispara el flujo interactivo estándar de Microsoft (login + MFA si aplica).
  5. Con el token obtenido, el portal llama a Microsoft Graph API para leer o escribir directamente en las listas de SharePoint que actúan como su base de datos.

2.2 Por qué este patrón

Se eligió deliberadamente NO tener un servidor propio ni una base de datos tradicional: todo el cómputo ocurre en el navegador del usuario, y la persistencia vive en listas de SharePoint dentro de sitios de Microsoft 365 ya existentes en el tenant. Esto reduce la superficie de mantenimiento (no hay servidores que parchar, no hay bases de datos que respaldar por separado) y aprovecha licenciamiento de M365 que la organización ya paga. El costo de hosting es $0 — GitHub Pages es gratuito para repositorios de este tipo.

2.4 Los tres tipos de tarjeta en U-Home

No todas las tarjetas de U-Home apuntan al mismo tipo de aplicación. Es importante distinguir tres categorías, porque cada una tiene un modelo de seguridad y de propiedad técnica distinto:

Tipo A — Aplicaciones de Power Apps (preexistentes al proyecto U-Home): U-Access y U-Solicitudes Mantenimiento son aplicaciones de Microsoft Power Apps, construidas dentro del tenant de Ubictum antes de que existiera U-Home. Por eso no se reconstruyeron como portales HTML — U-Home simplemente aloja una tarjeta con el enlace directo a la app ya existente. Su seguridad la gestiona nativamente la plataforma Power Platform / Dataverse del tenant, no el proyecto U-Home.

Tipo B — Portales HTML propios (construidos por BT): Alertas Operativas y Biométricos Colaboradores ya están en producción; Colaboradores Ubictum y U-Formularios están en construcción. Siguen el patrón técnico de la sección 2.1 — HTML + MSAL.js + Microsoft Graph, con su propia app registrada en Entra ID cada uno, gestionados completamente por BT.

Tipo C — Portales externos (administrados por terceros): BT Services Now (ServiceNow, gestionado en conjunto con Nadro) y HMS (Hardware Management System) son portales completamente ajenos a la infraestructura de BT Ubictum. U-Home únicamente aloja un enlace directo hacia ellos — no hay integración técnica, no comparten autenticación con el tenant, y cada plataforma define y administra su propia seguridad, fuera del alcance de este proyecto.

3. Seguridad y control de acceso

3.1 Modelo de seguridad decidido

La decisión de diseño central del proyecto: U-Home (el launcher) solo valida que la persona pertenezca al tenant de Ubictum — es un login simple, sin distinción de permisos internos. El control fino de "quién puede entrar a qué herramienta específica" NO vive centralizado en U-Home; vive en el registro de Entra ID de cada aplicación individual (Tipo B), mediante la opción "Assignment required = Sí" en su Enterprise Application, con grupos de seguridad asignados en "Users and groups".

Tener acceso a U-Home no implica tener acceso a ninguna herramienta específica — cada tarjeta Tipo B revalida el acceso de forma independiente al abrirse.

3.3 Vulnerabilidad detectada y corregida — sesión compartida entre subdominios

Durante el desarrollo se detectó una fuga de seguridad real: como U-Home y los 4 portales HTML propios viven bajo el mismo dominio raíz (btubictum.github.io), comparten el localStorage del navegador. El código original de autenticación confiaba en msalInstance.getAllAccounts() sin más validación — esto permitía que cualquier persona con una sesión válida en CUALQUIERA de los portales quedara marcada como "conectada" en los DEMÁS, sin que el sistema verificara si esa persona realmente tenía asignación de acceso a ese portal en particular.

Corrección aplicada en los cuatro portales (Alertas Operativas v16, Biométricos v11, U-Formularios v9, U-Home): cada aplicación ahora exige su propio acquireTokenSilent / ssoSilent específico contra SU PROPIA app registrada antes de conceder acceso, en vez de conformarse con la sola presencia de una cuenta en caché. La sesión persistente entre visitas se preserva únicamente para quien de verdad tiene asignación real en cada aplicación individual.

3.5 Seguridad de las tarjetas Tipo A y Tipo C

Las aplicaciones de Power Apps (U-Access, U-Solicitudes Mantenimiento) usan el modelo de seguridad nativo de la plataforma Power Platform / Dataverse del tenant de Ubictum — preexistente al proyecto U-Home y fuera de su gestión directa, aunque dentro del mismo tenant corporativo.

Los portales externos (BT Services Now, HMS) están completamente fuera del perímetro de seguridad de U-Home: no comparten autenticación con el tenant de Ubictum, tienen su propio login y sus propias reglas de acceso definidas por cada plataforma. U-Home no realiza ninguna validación antes de redirigir a estos enlaces — es responsabilidad exclusiva de cada plataforma externa proteger su propio acceso.

El proyecto no requirió contratar infraestructura de servidores, bases de datos, ni licencias adicionales: se apoya completamente en licenciamiento de Microsoft 365 que la organización ya tenía contratado para otros fines.

Biométricos Colaboradores

Visibilidad de checadas y control de incidencias de asistencia
Preparado para: Infraestructura, Arquitectura, Ciberseguridad, Consejo Técnico Elaboró: Héctor Herrera — Especialista BT Versión del documento: 1.0

1. Resumen ejecutivo

Biométricos Colaboradores es el portal interno que le da a Facilitadores, Líderes, Talento y Cultura (TyC), Enfermería y Administradores visibilidad sobre las checadas de entrada y salida del personal de almacén, y les permite capturar y dar seguimiento a incidencias de asistencia (faltas, permisos, incapacidades, vacaciones, descansos y retardos) con un control de permisos diferenciado por rol.

El portal forma parte del ecosistema de U-Home (tarjeta "Biométricos Colaboradores", color verde) y sigue el mismo patrón arquitectónico que el resto de las herramientas de BT: aplicación web estática sin servidor propio, autenticada contra Microsoft Entra ID, que usa Microsoft Graph API para leer y escribir directamente en listas de SharePoint que hacen las veces de base de datos.

A diferencia de otros portales del ecosistema, Biométricos Colaboradores tiene un modelo de seguridad interno considerablemente más elaborado: no basta con pertenecer al tenant de Ubictum — el acceso a cada pestaña, y la visibilidad de cada colaborador dentro de esas pestañas, depende de un catálogo de roles propio (CatAccesos) y de una jerarquía organizacional (Líder → Facilitador → Colaborador) que el portal resuelve en cada consulta. La sección 3 de este documento detalla ese modelo a fondo, incluyendo vulnerabilidades reales detectadas y corregidas durante su desarrollo.

1.1 Estado actual

El portal está en producción en https://btubictum.github.io/info_biometricos/, actualmente en la versión v98. Cuenta con 6 pestañas (Registros, Registros por Día, Registros por Semana, Registros por Biométrico, Registro Incidencias, y Carga de Data) y 7 listas de SharePoint como modelo de datos. La fuente original de las checadas es el sistema biométrico HikCentral Professional; la carga de esas checadas al portal es hoy un proceso manual (exportar de HikCentral y subir el Excel en la pestaña Carga de Data), con un flujo de automatización (RPA) en construcción — ver sección 2.6.

2. Arquitectura

2.1 Patrón general

Aplicación de una sola página (HTML + CSS + JavaScript), sin backend propio ni base de datos tradicional. La autenticación corre en el navegador vía MSAL.js contra la app registrada en Entra ID del portal; una vez autenticado, el JavaScript llama directamente a Microsoft Graph API para leer y escribir en las listas de SharePoint del sitio U-Biometricos (https://ubictum.sharepoint.com/sites/U-Biometricos), que actúan como base de datos relacional simplificada.

2.2 Fuente original de los datos: HikCentral Professional

Las checadas reales de entrada y salida se generan en HikCentral Professional (consola en 172.21.3.4), el sistema de control de acceso biométrico de la planta. Se evaluaron dos vías de integración directa que resultaron no viables:

  • OpenAPI de HikCentral: descartada porque el campo "Punto de acceso" (qué puerta/biométrico específico registró la checada) solo está disponible en la pantalla de Búsqueda de la consola, no en los reportes que expone la API.
  • Recepción automática por correo: descartada por la misma limitación de datos disponibles.

La vía operativa vigente es manual: exportar el Excel desde la pantalla de Búsqueda de HikCentral y subirlo en la pestaña Carga de Data del portal, replicando en software el mismo procedimiento que ya se hacía manualmente. La sección 2.6 describe la automatización de este proceso, actualmente en construcción.

2.5 Agrupación de checadas en sesiones (entrada/salida)

Una checada cruda es un solo evento (una hora, un biométrico). El portal agrupa las checadas de un mismo colaborador en "sesiones" de entrada/salida para poder mostrar horarios y calcular horas extra y retardos. La regla de agrupación distingue dos casos según la Jornada vigente del colaborador (consultada en vivo contra CatColab, no contra el dato histórico guardado en la checada):

  • Jornada diurna (no cruza medianoche): todas las checadas del mismo día calendario forman una sola sesión, sin importar cuántas horas pasen entre ellas — así un día largo con horas extra no se parte, y nunca se mezcla con el día siguiente aunque el hueco entre checadas sea corto.
  • Jornada nocturna (cruza medianoche, ej. 21:00–7:30): se agrupa por horas transcurridas desde la entrada (tope de 13 horas), lo que sí permite que la sesión cruce la medianoche correctamente.
  • Jornada desconocida (colaborador sin match en CatColab): se aplica el criterio diurno como respaldo seguro, ya que es el comportamiento correcto para la mayoría del personal.

Los checados registrados en el biométrico de la puerta del comedor ("Door_Panorama Comedor") no se muestran como hora de entrada/salida real en pantalla, ni se usan como base para calcular Retardo — se excluyeron de ambos cálculos porque no representan el ingreso o la salida real de la jornada laboral.

2.6 Automatización en construcción (RPA)

Se está construyendo un flujo de Power Automate Desktop que automatiza por completo el ciclo manual actual: inicia sesión en HikCentral, navega a la pantalla de Búsqueda, filtra por el rango de tiempo correspondiente, exporta el Excel, y lo sube directamente a la pestaña Carga de Data del portal. El plan es correr 3 flujos programados idénticos (1:00 a.m. con el filtro "Ayer", 7:20 a.m. y 11:00 a.m. con el filtro "Hoy"). Este proyecto requiere licencia de RPA desatendido (Unattended), una máquina virtual encendida de forma permanente, cuentas de servicio dedicadas, y una excepción de Acceso Condicional (MFA) para esas cuentas específicamente en esa máquina.

Al momento de este documento el flujo cubre login, navegación, filtro, exportación y descarga del archivo; queda pendiente el tramo de subida automática a Carga de Data.

Igual que el resto de los portales Tipo B del ecosistema, la app exige "Assignment required = Sí" en Entra ID, con los grupos U-Biometricos-Invitados y U-Biometricos-Colaboradores asignados como condición de entrada. Esta es la primera capa de seguridad — determina quién puede abrir el portal en absoluto. Las capas siguientes (qué pestaña, qué colaboradores) se resuelven por software, dentro de la aplicación, y se documentan a continuación.

3.2 Autorización por rol — catálogo CatAccesos

El acceso a la pestaña Registro Incidencias, y por separado el acceso a la pestaña Carga de Data, dependen de un catálogo propio (CatAccesos) que asocia el correo del usuario con uno o más roles: Facilitador, Lider, TyC (Talento y Cultura), Enfermera, o Admin. Una persona puede tener varios roles (un renglón por rol); sus permisos son la unión de todos los que tenga. Sin ningún rol asignado en CatAccesos, la persona ve una pantalla de "Sin acceso" — con el correo detectado y el detalle del error, para poder depurar el caso sin adivinar.

RolCódigos que puede capturarAlcance de colaboradores
FacilitadorF, PSG, V, DSolo sus propios colaboradores directos
LíderF, PSG, V, DSus directos, MÁS los de todos sus Facilitadores (árbol completo — ver 3.3)
TyC (Talento y Cultura)P, A, R, RJTodos los colaboradores, sin restricción
EnfermeraI, IITodos los colaboradores, sin restricción

Códigos: F = Falta, A = Asistencia, PSG = Permiso sin goce, P = Permiso con goce, I = Incapacidad (seguro social), II = Incapacidad interna, V = Vacaciones, D = Descanso, R = Retardo, RJ = Retardo justificado.

Los roles "elevados" (Admin, TyC, Enfermera) tienen dos privilegios adicionales que Facilitador/Líder no tienen: pueden editar días que ya tienen una checada biométrica real (los demás roles no pueden tocar esos días, aunque el código esté disponible en su lista), y pueden seguir corrigiendo una semana aunque ya esté formalmente cerrada.

Regla especial — Vacaciones (V): Facilitador y Líder solo pueden asignar el código V a partir de hoy o a fecha futura — no pueden marcar vacaciones en fechas ya pasadas. Admin es la única excepción y puede asignarlo en cualquier fecha, para corregir casos excepcionales.

3.3 Visibilidad jerárquica: árbol Líder → Facilitador → Colaborador

Un Líder no solo debe ver a los colaboradores que tiene asignados de forma directa — también debe ver a todos los colaboradores de cada uno de sus Facilitadores (segundo nivel del árbol organizacional). Esta regla se resuelve consultando, para el Facilitador de cada colaborador, cuál es a su vez el Líder de ESE Facilitador en CatColab vigente — sin depender de que el campo "Líder" de cada colaborador individual esté correctamente llenado a mano.

Esta visibilidad se resuelve consultando CatColab vigente en el momento de la consulta, nunca el dato histórico que quedó grabado en la checada al momento de subirla — así, si la asignación de Facilitador o Líder de alguien cambia, la visibilidad se actualiza sola la próxima vez que alguien abra la pestaña, sin necesitar ninguna corrección manual sobre datos ya guardados.

3.4 Restricción de acceso a Carga de Data

La pestaña Carga de Data —desde donde se suben las checadas nuevas y se ejecutan herramientas de reparación de datos maestro, cálculo de horas extra, reapertura de semanas cerradas, y actualización masiva de CatColab— está restringida exclusivamente a los roles TyC y Admin del mismo catálogo CatAccesos. El resto de los roles no pueden siquiera abrir la pestaña.

Dado que varias de estas herramientas modifican datos en lote (potencialmente cientos de registros de una sola vez), todas siguen el mismo patrón de seguridad operativa:

  • Ninguna acción se ejecuta directo — primero se busca/compara y se muestra un resumen (cuántos colaboradores, cuántos registros) antes de tocar nada.
  • Casillas de selección por renglón (marcadas o desmarcadas según el riesgo de la acción) para que el administrador decida exactamente qué aplicar, no todo-o-nada.
  • Modal de confirmación propio (no el confirm() nativo del navegador) antes de cualquier escritura, mostrando el número exacto de registros afectados.
  • Los cambios masivos se ejecutan en lotes de 20 (límite técnico de Microsoft Graph por llamada) con registro de progreso visible.

3.5 Permisos de listas de SharePoint — lección operativa

Se detectó más de una vez el mismo patrón de falla: una lista de SharePoint con permisos únicos (no heredados del sitio) devuelve 0 registros o un error 403 sin ningún mensaje claro para quien no tiene permiso de lectura específico sobre ESA lista en particular — ocurrió primero con CatAccesos y después con Log. La lección operativa incorporada al portal: ante un 403 o un conteo de "0 registros" sin razón aparente, lo primero a revisar son los permisos únicos vs. heredados de esa lista puntual, no el código de la aplicación.

3.6 Vulnerabilidad de sesión compartida entre portales — corregida

Como Biométricos Colaboradores comparte dominio raíz (btubictum.github.io) con los demás portales del ecosistema, se detectó la misma vulnerabilidad de localStorage compartido documentada en el proyecto U-Home: el código validaba la sola presencia de una cuenta en caché del navegador, sin confirmar que esa cuenta tuviera asignación real de acceso a Biométricos específicamente. Corregido exigiendo acquireTokenSilent / ssoSilent propio de esta app antes de conceder acceso — mismo criterio aplicado en los demás portales del ecosistema.

3.7 Incidentes de integridad de datos corregidos

Aunque no son vulnerabilidades de acceso, los siguientes incidentes comprometieron la integridad de los datos y se documentan aquí porque su causa raíz y su método de diagnóstico son relevantes para cualquier auditoría de seguridad de la información del portal:

  • Fecha corrida un día: guardar una fecha-sin-hora como medianoche UTC (T00:00:00Z) hacía que SharePoint la reinterpretara en hora local de México y la corriera un día hacia atrás. Corregido guardando siempre a mediodía UTC (T12:00:00Z), fuera del rango de reinterpretación de cualquier zona horaria del país.
  • Rechazo masivo de inserciones ("generalException"): una columna (HoraExtra) se había creado como texto en SharePoint en vez de número; el código enviaba un valor numérico, y el choque de tipos producía un error genérico sin relación aparente con la causa real. Afectaba silenciosamente solo a los registros elegibles para horas extra. Corregido igualando el tipo de columna, sin cambios de código.
  • Visibilidad jerárquica incompleta para Líderes (ver 3.3): un Líder no veía a los colaboradores de sus Facilitadores, solo a los suyos directos — corregido resolviendo el segundo salto del árbol organizacional en cada consulta.

4.2 Versionado y despliegue

No existe un pipeline de CI/CD formal — cada actualización se publica subiendo directamente el archivo HTML corregido al repositorio, lo cual publica la nueva versión de inmediato en GitHub Pages. El portal mantiene un número de versión visible en pantalla (actualmente v98) para poder rastrear qué build está corriendo en producción en cualquier momento dado.

4.3 Automatización planeada — infraestructura adicional requerida

El proyecto de automatización descrito en la sección 2.6 introduce, a diferencia del resto del portal, dependencias de infraestructura tradicionales que hoy no existen en Biométricos Colaboradores:

  • Una máquina virtual (o servidor) encendida de forma permanente para correr los flujos programados.
  • Licencia de Power Automate Desktop en modalidad Unattended (desatendido), necesaria para ejecutar flujos sin un usuario presente frente a la pantalla.
  • Cuentas de servicio dedicadas para iniciar sesión tanto en HikCentral como en el portal.
  • Una excepción de Acceso Condicional (MFA) para esas cuentas de servicio, limitada específicamente a esa máquina.

5.2 Enrutamiento de autoría al guardar una incidencia

El campo que registra "quién hizo el cambio y cuándo" depende de tres condiciones evaluadas en este orden de prioridad:

  1. Si quien guarda tiene rol Enfermera (aunque tenga otros roles también): siempre se registra en ModificadoPorEnfermeria — Enfermería puede capturar I/II en cualquier momento, sin depender del ciclo de cierre semanal.
  2. Si no es Enfermera y la semana ya estaba cerrada: se registra en ModificadoPorTyC — es una corrección posterior de un rol elevado.
  3. Si no es Enfermera y la semana no estaba cerrada: se registra en GuardadoPor — flujo normal, para cualquier rol incluido Facilitador/Líder.
